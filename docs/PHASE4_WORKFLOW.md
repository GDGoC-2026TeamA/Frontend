## 예시 동작과 보관 범위

- 기본 업무 두 개, 절차 카드 두 개와 작업 두 개는 Figma 예시입니다. 새 작업과 카드는 같은 탭의 메모리에 추가됩니다. 새로고침하면 예시로 초기화됩니다. 계정 인증이나 서버 권한을 구현한 것은 아닙니다.
- 홈에서 고른 업무 ID를 작업 화면으로 전달합니다. 예약 업무에 재고 전표나 품목 코드를 섞지 않습니다. 알 수 없는 업무나 기록은 오류 또는 자료 부족 상태로 표시합니다.
- 자료 입력, 초안, 수정, 검토 완료와 저장 결과를 분리합니다. 초안의 수량을 그대로 정답으로 취급하지 않습니다. 실제 수량은 0 이상의 정수이며, 차이 사유와 확인 표시가 필요합니다. 예약은 변경 시간과 예약 가능 여부를 확인해야 합니다.
- 수정 취소는 편집 중인 값만 버립니다. 확인한 수정은 작업 기록에 남겨 작업 내역에서 다시 엽니다. 저장한 결과와 카드의 기준 자료는 복사해 업무 수정과 분리합니다.
- 같은 결과에서 카드를 두 번 저장해 중복 생성하지 않습니다. 카드 이름 수정은 해당 카드만 바꿉니다. 공유받은 업무 기준은 읽기 전용이고, 내가 등록한 업무의 정보만 수정합니다.
- 기본 홈의 재고 업무는 앞선 차수의 공유받은 업무 예시이므로 상세 수정이 막혀 있습니다. 예약은 내가 등록한 업무 예시입니다. Figma의 소유자 상세 상태도 같은 화면에서 구분합니다.
- 예시 자료만 화면 흐름에 쓰며 실제 파일을 읽거나 업로드한 것처럼 표시하지 않습니다. 실제 파일은 데모에서 미연결 안내가 나옵니다.
- WORK BRIDGE의 결과 저장은 외부 재고 시스템 등록, 실제 예약 가능 여부 조회나 예약 확정을 마쳤다는 뜻이 아닙니다.

## API 트래커 기준

2026-11-21 한국 시간에 [팀 API 작업 트래커](https://app.notion.com/p/22d3a23d4c0e8325bff901f4cb073d84)의 작업 시작, 첨부, 초안, 수정, 결과, 상세, 카드와 다운로드 항목을 직접 읽고 대조했습니다. API는 프론트엔드가 요청하고 응답을 표시하는 범위만 구현했습니다. 서버나 데이터베이스는 만들지 않았습니다.

| 작업                  | 프론트엔드 요청                                                              |
| --------------------- | ---------------------------------------------------------------------------- |
| 작업 생성             | POST tasks/{taskId}/jobs, `{ name, description }`                            |
| 파일 첨부             | POST jobs/{jobId}/files, FormData의 file 바이너리                            |
| 초안 생성             | POST jobs/{jobId}/draft, `{ fileIds }`                                       |
| 수정과 확인 상태      | PATCH jobs/{jobId}/draft, `{ fields: [{ key, value, checked }], lastField }` |
| 결과 저장             | POST jobs/{jobId}/result, 요청 본문 없음                                     |
| 기록 다시 열기        | GET jobs/{jobId}, 수정 값과 pending, lastField 읽기                          |
| 카드 상세와 이름 수정 | GET cards/{cardId}, PATCH cards/{cardId}에 `{ title }`                       |
| 결과 다운로드         | GET jobs/{jobId}/result/download, 바이너리와 Content-Disposition             |

기본 API 주소는 기존 `/api/v1` 기준을 씁니다. 작업 ID, 작업 파일 ID와 기준 자료 ID를 섞지 않습니다. 첨부나 초안 요청 실패 시 이미 받은 작업 ID와 첨부 ID를 재사용합니다. 취소된 초안의 늦은 응답은 화면에 붙이지 않습니다. 취소는 이미 서버에 생긴 작업이나 첨부의 삭제를 뜻하지 않습니다. 서버의 처리 상태를 알 수 없는 실패는 화면에 남겨 확인할 수 있게 합니다.

API 모드는 서버가 돌려준 필드와 누락 키를 표시하며 예시 수량이나 매뉴얼 구절을 붙이지 않습니다. source의 자료 ID와 위치만 표시하고 인용문은 만들지 않습니다. 서버 작업의 원본 비교 화면, 항목별 한글 레이블과 값 형식의 전체 범위는 추가 합의가 필요합니다. lastField는 마지막 수정 필드로 보내며 이어하기 응답에서도 보관합니다.

업무 이름과 설명을 수정하는 PATCH tasks 계약은 트래커에 없어 API 모드에서는 수정 저장을 막았습니다. 서버 카드 생성에는 실제 analysisItemId가 필요한데 현재 작업 응답에 없어 서버 결과의 카드 저장도 막았습니다. 다른 ID를 대신 보내지 않습니다. API 카드 제목 수정과 상세 조회는 연결했습니다. 다운로드 파일명을 읽으려면 서버가 Content-Disposition을 CORS에 노출해야 합니다.

## 검사와 캡처

- 기존 UI 검사 41개와 4차 검사 9개를 합한 50개를 실행합니다. 이전 빈 목록과 파일 오류 검사는 `?empty=1`과 `?fixture=read-error`라는 명시적인 예시 상태로 남겼습니다. 기본 정상 흐름을 오류로 고정하지 않습니다.
- 모델 검사는 기존 학습 3개와 작업 3개입니다. 미확인 저장 차단, 원본과 결과의 분리, 업무별 절차, 카드 중복 방지를 확인합니다.
- UI 검사는 재고와 예약 저장, 수정 취소와 이어하기, 카드 수정과 검색, 상세 권한, 320px부터의 레이아웃과 접근성을 확인합니다.
- API 검사는 브라우저에서 모의 응답을 씁니다. 실제 서버 성공을 검증하는 검사가 아닙니다. 요청의 JSON, 파일 바이너리, 재시도 ID, 본문 없는 결과 저장과 다운로드를 확인합니다.
- 팀의 `workbridge-qa.spec.js` 서버 통합 QA는 수정하지 않았고 이번 UI 검사와 별도로 남겼습니다.
- 통과한 UI 검사에서 4차 화면 캡처 15개를 만들고 기존 절차와 새 절차 비교 화면과 함께 PR에 첨부합니다.

검증 상태: lint, build와 모델 검사 6개가 통과했습니다. 전체 실행에서 기존 UI 41개가 통과했고, 실패한 문구를 수정한 뒤 4차 UI 9개가 모두 통과했습니다. 업로드 명령에서는 UI 50개를 함께 다시 검사합니다. 실제 서버 통합 QA는 별도입니다.

3차 PR #22가 main에 병합된 뒤 최신 main에서 새 이슈의 `feat/#번호` 브랜치를 만듭니다. 기능, 디자인, 검사와 문서 커밋을 나누고 main 대상 PR에 close 연결과 리뷰 요청을 씁니다. 팀원 리뷰와 승인 후 팀에서 병합합니다. 업로드 보조 파일은 저장소에 넣지 않습니다.
